# ntfy登録・権限設定の自動化

Node.js＋自前ntfyを維持し、端末ごとのユーザー作成・トピック読み取り許可・解除を自動登録APIと限定管理プロセスへ切り替えました。ランダムな`up...`トピック名は維持します。VPS配備・公開HTTPSでの権限検証、基本通知経路・状態遷移・復旧に加え、管理サービス停止／復旧・VPS再起動後の登録保持・暗号化プッシュ配送も確認済みです。運用・負荷確認は残っています。最新の確認範囲は[進捗](server-progress.md)を参照してください。

消灯中の受信は2026/10/24の利用者報告で成功例を確認しました。長時間消灯後の検証は保留し、ベータテストで確認します。追加検証全体を完了扱いにはしません。

## 段階と完了条件

1. **ntfy管理操作の基盤（実装済み）**：サーバー内の管理アダプターを作り、ntfy 2.32.0の一時DBで、一般ユーザーの作成・単一トピックの読み取り許可・解除・削除を検証しました。既存VPSのユーザーやACLは変更しません。
2. **認証済みAPIと永続化（実装・VPS結合確認済み）**：端末UIDと資格情報・トピック所有者を束縛し、状態と管理ジョブを永続化しました。作成・通知先更新・停止・削除の再試行と再起動復旧を実装しています。別端末の横取り・重複割当てを拒否し、所有確認までは募集を送信しません。管理サービス停止中の登録保留からの自動回復、VPS再起動後の資格情報・到達確認済み購読の保持も実環境で確認しました。
3. **Androidの登録画面（実機の状態遷移・復旧確認済み）**：発行結果と接続先を表示し、ntfy設定を案内します。ランダムなトピック名を運用者へ渡す操作をなくしました。利用者によるログイン情報のコピー・ntfyへの貼り付け・監視開始・通知受信に加え、停止・削除・端末再起動などの状態遷移・復旧確認は完了済みです。
4. **VPSでの結合確認（基本経路・停止／復旧・再起動確認済み）**：公開HTTPSで実ntfyへの登録・更新・停止・再開・削除と権限失効、管理サービス停止中の保留登録の自動回復、VPS再起動後の自動起動・登録保持・検証用通知先への暗号化配送を確認しました。実機ntfyの自動再接続も確認済みです。長時間消灯後の検証はベータテストへ保留し、運用・負荷・正式配布は未完了です。

第1段階だけでは新規利用者の登録は自動化されません。既存の`device001`と手動ACLは維持されます。自動移行や自動削除は行いません。

## 第1段階の管理操作

`server/ntfy-admin.ts`は、信頼されたサーバー内の呼び出し元にだけ使う部品です。HTTP API・管理用公開エンドポイント・ntfy DBの直接SQL編集は追加しません。

- 端末認証が発行したUUIDから専用の`sur_...`ユーザー名を決定し、任意のユーザー名や管理者名を入力させません。
- パスワードは256bitのランダム値を生成します。呼び出し元は生成結果を保存してから作成を依頼し、再試行では同じ値を使います。既存ユーザーのパスワードは作成の再送で変更しません。保管・認証済み端末への返却は第2段階です。
- 作成するロールは`user`のみ。許可するのは指定した`up...`トピック1件への`read-only`のみです。ワイルドカード・URL・制御文字を受け付けず、匿名・全ユーザー・全トピックへの許可は操作できません。トピックが本人のものかの束縛は第2段階の責務です。
- 解除はユーザーとトピックを指定して行います。アカウント削除も専用ユーザー1件に限定し、存在しないユーザーの再削除は完了として扱います。
- 実行ファイルと設定ファイルは運用者が設定する絶対パスに固定し、シェルを使わず引数配列で実行します。実行時間・出力サイズを制限し、CLIの生の出力をAPIエラーやログへ渡しません。
- パスワードは`NTFY_PASSWORD`環境変数で子プロセスへ渡し、引数には含めません。親の`NTFY_*`変数は引き継がず、別DBやハッシュへの意図しない上書きを防ぎます。同一OSユーザー・rootからの環境参照を防ぐものではありません。

CLIがntfyの認証DBへアクセスするため、第2段階ではntfy用ユーザーで動く限定管理プロセスへ分離します。Node.jsのAPIサービスへroot権限や無制限のsudo権限を与えたり、認証DBを公開領域へ置いたりしません。既存のsystemd定義は変更せず、管理プロセスの配置は運用者が行います。

## 第2段階の実装契約

- 認証済み端末だけが`/v1/ntfy-registration`をGET・PUT・DELETEできます。PUTは`{topic: "up..."}`、DELETEは空の要求とし、任意のユーザー名・資格情報を受け付けません。GETは本人の発行結果と管理状態を返します。
- トピックは端末間で一意に予約し、作成前に資格情報と希望状態をSQLiteへ保存します。管理状態は`pending`・`ready`・`stopped`で表し、失敗時は秘密を含まないエラーと次回試行時刻を保存します。
- 通知先変更は旧権限を解除してから新権限を付与します。停止と端末削除はアカウント削除ジョブを残し、端末削除のカスケードで復旧情報を失わないようにします。処理中の変更は世代で区別し、古い完了を採用しません。
- 募集配送と所有確認チャレンジは、本人の予約トピックが`ready`の場合だけ許可します。既存の手動管理端末は登録レコードを持たないため従来の所有確認を維持します。
- 管理操作は限定されたローカルUnixソケット経由で呼び出し、APIプロセスへntfy認証DBのアクセス権を与えません。ソケットと管理プロセスは運用者が専用ユーザー・権限で配置します。

### ローカル管理プロセスの配置

`pnpm build:server`は`dist/server/ntfy-admin-main.mjs`も生成します。管理プロセスだけをntfy認証DBへアクセスできる専用ユーザーで起動します。APIユーザーはソケットの共有グループにだけ参加させ、認証DB・ntfy設定の読み取り権限やsudo権限は与えません。管理プロセスの侵害はntfyアカウント管理権限の侵害になるため、ソケットを公開プロキシへ接続しません。

管理プロセス用の非公開環境設定：

```sh
SURENECO_NTFY_ADMIN_SOCKET=/run/sureneco-ntfy/admin.sock
SURENECO_NTFY_BIN=/usr/local/bin/ntfy
SURENECO_NTFY_CONFIG=/etc/ntfy/server.yml
```

ソケットの親ディレクトリーは運用者が管理ユーザーとAPI共有グループを所有者として作り、`0750`にします。管理サービスは同じグループで起動し、ソケットは`0660`で作成されます。既存パスは自動削除しません。異常終了でソケットが残った場合は、旧プロセスが停止していることを確認してから運用者が撤去してください。

```sh
node dist/server/ntfy-admin-main.mjs
```

API用環境へ同じ`SURENECO_NTFY_ADMIN_SOCKET`だけを追加して再起動すると、登録APIと永続ジョブの処理を有効にします。未設定時は自動登録APIを無効にし、従来の手動登録を維持します。管理プロセスの停止時も希望状態を保存し、復旧後に再試行します。APIのSQLiteには本人へ再表示するntfyパスワードを保存するため、DB・バックアップを秘密情報として保護してください。

登録APIは既存の端末Bearer認証を要求します。GET・PUT・DELETEの成功応答は`{registration: ...}`で、他端末の資格情報は返しません。`ready`はACL管理の完了であり、所有確認チャレンジやAndroid配送の成功を示しません。Android画面は第3段階で接続し、実VPSへの配置と基本の端末配送は第4段階で確認しました。

### 第4段階の配備ファイルと確認範囲

`server/sureneco-ntfy-admin.service`と`server/ntfy-admin.env.example`を管理プロセス専用に使います。`server/sureneco-ntfy-admin.conf`はAPIサービス用drop-inで、ソケットの共有グループだけを追加します。APIへntfy DBの権限は付けません。管理プロセスのランタイムディレクトリーはsystemdが作成・撤去し、手動起動時は既存ソケットを自動削除しません。

配備前に対象コミット、実ntfyのバイナリーパスとバージョン、設定・DBのパスと所有権、既存サービス定義を確認します。既存の設定・DB・同名APKは上書きしません。公開APIの疎通だけで自動登録や端末配送の成功とは判断しません。

## 第3段階のAndroid接続契約

- 同意して中継登録し、固定ntfy originの`up...`通知先を受け取った後、端末Bearer認証で登録APIへPUTします。`ready`になるまで購読チャレンジを開始しません。画面表示中の状態確認と「同期を再試行」で管理状態を再取得します。
- 接続先・端末ユーザー名・パスワードを通知設定画面に表示します。パスワードは初期状態で隠し、利用者の操作で表示します。資格情報は端末専用保存領域へ保存し、ログ・通常の設定エクスポートには含めません。運用者へトピックを伝える操作は不要になります。ntfyアプリへの初回ログインは利用者が行います。
- ログイン情報はntfyの入力欄に対応する接続先URL・ユーザー名・パスワードを分けて表示し、それぞれ専用のコピーボタンを設けます。コピーはAndroidのクリップボードへ直接書き込み、パスワードは非表示のままコピーできます。Android対応版ではパスワードを機密情報としてマークし、システムのプレビューを抑止します。コピーの成功・失敗だけを表示し、パスワードを完了メッセージへ含めません。クリップボード履歴等に残る可能性を案内します。
- 通知先・設定・停止の世代が変わった後に届いた古い応答は採用しません。停止・削除は通信前に端末通知を抑止します。圏外ではサーバー未反映を維持し、再試行できます。
- 停止要求の受付とntfyアカウント撤去完了を区別し、登録GETで`stopped`を確認するまで権限撤去済みとは表示しません。端末削除後は認証を破棄するため、サーバー受付済みと表示し、非同期の権限撤去完了を確認したとは表示しません。
- 自動登録APIが利用不可の場合は失敗を表示し、手動登録へ黙って切り替えません。既存のサーバー側手動アカウントは変更しません。

## 利用者の初回操作

Google Play版・F-Droid版のntfyを利用できます。自前サーバーへの配送ではGoogle Play版もFirebaseを使いません。ntfyアプリ自身のサーバー・ログイン設定を他アプリから自動投入できる公開方式は、今回確認できた範囲では見つかっていません。初期の配布版ではntfyの導入と初回ログインは利用者が行う前提で、サーバー側のユーザー発行とACL設定を自動化します。完全な無操作登録とは区別します。

トピックは自動作成されますが、ntfyアプリに保存済みのログイン情報は自動更新されません。ログイン情報欄では赤字・太字で、表示されたユーザー名とパスワードを両方コピーして置き換えるよう注意します。同じ接続先のユーザーが既にある場合は、そのユーザーを編集して保存してください。サーバー登録の削除後に再登録した場合も、新しい資格情報への置き換えが必要です。

## 検証

```sh
pnpm exec vitest run tests/ntfy-admin.test.ts
```

実際のntfyバイナリーを使う結合テストはLinuxで行います。公式配布物とチェックサムを確認し、検証用バイナリーの絶対パスを指定します。テストが一時ディレクトリーへ専用設定・認証DBを作るため、本番の設定・DBは使いません。

```sh
SURENECO_TEST_NTFY_BIN=/absolute/test/ntfy pnpm exec vitest run tests/ntfy-admin.integration.test.ts --maxWorkers=1
```

指定しなければ実バイナリーのテストはスキップします。API接続・Android自動同期・VPS配備・実配送の自動化完了をこのテストだけで判断しません。

2026/10/23に公式チェックサムと照合したntfy 2.32.0で検証しました。単体テスト8件と実バイナリーの結合テスト1件が成功し、別ユーザー・別トピックへのアクセス拒否、書き込み拒否、権限解除とユーザー削除の反映を確認しました。`pnpm test:server`でも管理アダプターのテストを実行します。

第2段階では型チェックとサーバー67テストに合格しました。公式配布物のSHA-256と照合した同じntfy 2.32.0を起動し、実HTTP API・Unixソケットの管理プロセス・永続SQLiteをつないだ実行確認も行いました。登録後の読み取り200、通知先変更後の旧トピック403／新トピック200、停止後401、保留登録の再起動復旧後200、端末削除後の再起動をまたぐ撤去後401を確認しました。この段階ではAndroidの配送・実VPSの自動登録は未確認でした。

第3段階では、Android登録ライフサイクル21テストとKotlinコンパイル、通知設定画面17テスト、型チェック・フロントエンドビルドを確認しました。登録前後・停止／削除・トークン更新中の古い応答、API失敗からの再試行を検証しています。ブラウザーの390px幅で実際のReact画面を操作し、パスワード表示／状態変更後の再マスク、未反映状態と削除受付表示、横方向のはみ出しがないことを確認しました。この画面確認には状態入力用の一時fixtureを使っており、Androidネイティブ・実APIとの結合配送の証明ではありません。この段階では接続済みAndroid端末がなく、ntfy実ログインと端末配送は未確認でした。

Android側のライフサイクルとコンパイルを確認するコマンド（`src-tauri/gen/android`で実行、SDKパスを環境へ設定）：


Rust JNIの再生成や新APKの作成を伴う確認とは区別します。

第4段階ではVPS上のNode.js 24.22.1・ntfy 2.32.0で型チェック・サーバー67テスト・systemd定義検証に合格しました。配備後の公開HTTPSを通し、一時2端末の本人読み取り200・他端末読み取り403・トピック横取り409・書き込み403、通知先変更後の旧トピック403／新トピック200、停止後401、再開後200を確認しました。最後に両検証端末を削除し、API認証・ntfy認証とも401になったことを確認しました。検証用資格情報は資料へ保存しません。利用者から2026/10/23にAndroid実機の基本経路と通知受信、2026/10/24に状態遷移・復旧確認の完了報告を受けました。消灯中の未受信とサーバー側の管理サービス停止／復旧・VPS再起動の確認は残っています。

2026/10/24に、利用者による管理サービス停止とVPS再起動の操作後、SSH・公開API・実ntfyで復旧を直接確認しました。停止中の`pending`・`ntfy_admin_failed`から再送なしで`ready`となり、同じ資格情報で読み取り401→200へ回復しました。VPS再起動後の自動起動・登録と購読の保持・通知先更新、実APIから暗号化プッシュを送り復号してチャレンジを返す経路も成功しました。実機ntfyは自動再接続し、実機の資格情報は変更していません。検証用端末は削除し、API・ntfy認証の失効とDB内の登録・ジョブ撤去を確認しました。上記の復旧未確認という記録は以前の段階です。詳細と確認範囲は[進捗](server-progress.md)を参照してください。
