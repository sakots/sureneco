# Node.js＋VPSで人数制限を設けない場合の費用

2026/10/22確認。[運用方式全体の比較](operation-cost.md)と[実装進捗](server-progress.md)を併せて参照してください。契約済みホームページスペースの料金は含めません。Node.js＋UnifiedPush＋自前ntfyを採用しましたが、契約先・容量は未決定です。実装は再開しましたが、契約・増強・配備は行っていません。

## 「ユーザー無制限」の意味

登録人数を料金プランで制限せず、誰でも利用できるサービスにはできます。VPSは通常、利用者が1人増えるたびに自動で従量課金される仕組みではありません。一方、一定額のVPSでどれだけ利用者が増えても1分程度の通知を維持できる、という保証はできません。

費用を左右するのは登録者数だけでなく、**有効な監視購読を持つ端末数、監視するスレッド数、条件の種類、新規レス数と通知送信件数、ntfyの同時接続数・再接続頻度**です。端末がアプリを閉じていてもサーバーは監視を続けるため、画面を開いている人数だけで負荷を見積もりません。

公開時は「登録人数の上限なし」と「一定の料金で無限の負荷を処理できる」を区別します。現行の試作に登録人数の固定上限はありませんが、大規模な負荷試験はしておらず、「無制限対応済み」とは案内しません。

## VPSの料金例

キャンペーンや長期一括払いを前提にしないLinux VPSの月額上限です。税込の公式表示による比較で、価格以外の性能・可用性が同じという意味ではありません。

| サービス | メモリ・CPU | 月額上限 | 用途の考え方 |
| --- | --- | ---: | --- |
| WebARENA Indigo | 1GB・1vCPU | 449円 | 最小費用での動作・負荷検証候補 |
| KAGOYA CLOUD VPS | 1GB・1コア | 550円 | 同じく検証候補 |
| KAGOYA CLOUD VPS | 2GB・2コア | 770円 | 継続公開の初期構成として比較する候補 |
| WebARENA Indigo | 2GB・2vCPU | 814円 | 同上 |
| WebARENA Indigo | 4GB・4vCPU | 1,630円 | 実測で増強が必要になった場合の比較候補 |
| KAGOYA CLOUD VPS | 4GB・4コア | 1,760円 | 同上 |

出典：[WebARENA Indigo公式料金](https://web.arena.ne.jp/indigo/price/)、[KAGOYA公式料金](https://support.kagoya.jp/vps/charge/index.html)。KAGOYAは税込目安で丸めにより差が出る場合があります。Indigoはインスタンスを停止しても廃棄するまでは課金されます。契約前に料金・提供条件・変更手順を再確認します。

確認した候補では、最小費用の検証は月449円の1GB、2GBからの公開は月770円の候補があります。追加月額は概ね**VPS＋必要なバックアップ・転送等のオプション**です。採用構成ではFirebaseは使わず、ntfyを同じVPSで運用します。

これは1GBで何人、2GBで何人まで処理できるという実測結果ではありません。1GBはOS・Node.js・ntfyと判定ワーカーを同時に動かす余裕を測る段階、2GBは公開候補として負荷試験する段階とします。低価格だけで1分通知や人数無制限の性能を保証しません。

## 費用を増やさないための構成

```text
契約済みのホームページスペース
  └─ 案内・ダウンロードリンク・プライバシーポリシー

Node.jsのVPS（初期は1台）
  ├─ 購読API・認証
  ├─ スレッドごとに共有する取得と解析
  ├─ 共通部分をまとめた判定と、利用者別の条件判定
  ├─ SQLite・期限付きの通知イベントと送信待ち
  └─ 自前ntfy → Androidのntfyアプリ → スレネコチェッカー
```

同じ3スレッドを1,000端末が監視する場合、5chからの取得は原則スレッド単位の3回を共有する設計にします。3,000回取得する設計にはしません。ただし、取得回数を共有しても、その後の端末別条件の判定と送信先ごとの配送がなくなるわけではありません。

利用者が増えても共通のパースを毎回やり直さないこと、同じ条件の判定をまとめること、条件変更時だけ必要な情報を同期すること、期限後の履歴を掃除することで負荷を抑えます。NG・許可ワッチョイ・締め・期限・ユーザー定義正規表現の意味は維持し、個別設定を省略して件数だけ増やす実装にはしません。

ntfyでも通知先を端末ごとに持ち、NG・許可ワッチョイ等の個別条件を送信前に適用します。共通トピックで全員へ同じ募集を配る案にはしません。

## 現行試作の限界

現在のNode.js試作は板・datの取得とdat解析を監視回で共有していますが、購読ごとの判定ではワーカーを起動します。スレッド・条件が同じ利用者間でも、すべての判定結果を共有する実装にはなっていません。多数の購読で1監視回の予算を使い切ると、未処理の購読は次回へ回るため、通知の遅れが増えます。

送信待ちの処理も1回の件数・時間を制限しています。締めや期限切れを送らない設計を維持するため、負荷が増えたら無制限に並列化するだけでは解決しません。DBの更新競合、ワーカー起動回数、ntfy送信待ちを測り、共通判定の再利用と上限付き並列配送等を検討します。これらの最適化はまだ実装していません。

大きくなっても最初からRedis・外部DB・複数VPSを契約する必要はありません。まず単一VPSとSQLiteで実測し、DBロックや処理時間が問題になったときに、プロセス分割・DB変更・複数台化を比較します。

## ntfyの負荷と制限

自前ntfyでは接続維持も自分のVPSが担当します。中継アプリの同時接続、再接続集中、ファイル記述子、プロキシの接続上限、キャッシュ容量と配送レートを確認します。特にNode.jsから同じ送信元で大量配信するときの制限を、想定端末数で検証します。[ntfyのスケール設定](https://docs.ntfy.sh/config/#tuning-for-scale)

既定制限をすべて外して無制限を保証する運用にはしません。APIの端末登録・チャレンジと配送にも頻度上限を設け、ntfyの認証とトピックACLを検証します。Firebase認証・App Checkの代替は自前の端末別認証で、APKの真正性を検証する保証はありません。

## 増強の判断

人数だけの「100人まで・1,000人まで」という表は、実測前には作りません。小規模な検証から始め、少なくとも次を記録します。

- 投稿から監視検出・ntfy受付までの時間と、実端末での受信時間。1分程度の目標から外れていないか。
- 1監視回の所要時間、処理を次回へ残した回数、購読ごとの最終取得成功時刻。
- 送信待ちの件数・最古の経過時間、期限内に送れず破棄した件数。
- CPU・メモリ・DB容量・ロック待ち、同時に動くワーカー数。
- ntfyの同時接続、再接続数、キャッシュ・転送量、ファイル記述子とプロキシ上限。

この結果が目標を超えた場合に2GB→4GB等の増強や判定の共通化を検討します。予算を月770円に固定したまま際限なく利用者が増える場合は、1分通知を維持する保証はできません。公開条件と運用予算を分けて決める必要があります。

費用と運用自由度を両立する案としては、登録人数の固定上限を設けず、2GB級の小規模VPSで負荷試験してから公開し、利用量を見て増強する方式が候補です。採用構成はNode.js＋自前ntfyですが、現時点でVPSの契約・配備はしていません。既存スペースは掲載用として使います。
