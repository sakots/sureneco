# UnifiedPush通知の実装進捗

2026/10/24時点では、自動登録APIと限定管理サービスのVPS配備・公開HTTPSでの権限検証、利用者によるAndroid実機の通知受信・状態遷移・復旧確認まで完了しています。同日の追加報告で消灯中の受信にも成功しました。長時間消灯後の検証は保留し、ベータテストで確認します。管理サービス停止／復旧・VPS再起動、運用・負荷、正式配布・Play公開の準備は残っています。[段階別の計画](ntfy-registration-automation.md)も参照してください。

## 実装したもの（2026/10/22時点）

以下の実装・検証は2026/10/22に実装を再開した時点の記録です。当時の作業ブランチは`feat/unifiedpush-ntfy`で、Node.js＋VPSの監視とUnifiedPush＋自前ntfyの方針に沿い、Firebase版の試作を置き換えました。当時はVPS配備・実ntfy配送・実端末確認・Play公開を行っていませんでした。

- `server/device-auth.ts`：256bit端末別トークン、ハッシュ保存、更新・失効・本人の端末削除。公開APIの発行・入力・頻度を制限。
- `server/channels.ts`・`subscriptions.ts`：通知先と鍵の登録、5分有効の一回限りチャレンジ、所有確認前の無効化、設定リビジョンと通知先世代、停止・削除・再送。
- `server/web-push.ts`：Web Pushのaes128gcm暗号化・VAPID・TTL、ntfy専用ヘッダー、固定HTTPS origin、既知クエリーの正規化、DNS/IP検査と解決先固定、タイムアウト。鍵生成スクリプトを追加。
- `server/store.ts`・`monitor.ts`・`scheduler.ts`・`delivery.ts`：SQLite排他と永続化、共有取得とTypeScriptコアの隔離実行、期限内で最大5回の再試行。旧Firebase SDK・ワーカー・設定・依存を削除。
- Android：connector 3.3.5、中継選択・登録・解除、端末専用保存、ネイティブ受信・通知、期限・重複・世代・権限・停止確認。古い同期応答を採用しないため端末内でも更新世代を確認。
- モバイル画面：通知同意・未導入・確認待ち・未同期・再試行・停止・削除。PC専用操作とGitHub更新を表示せず、Androidの更新間隔は60秒以上。表示中の一覧更新とOS通知を分離。
- APK基盤とAAB生成用コマンド・署名設定。systemd・API/ntfyのNginx・ntfy設定例、[導入準備](node-vps.md)と[Play提出資料の下書き](google-play.md)。

旧PHP実装・専用テスト・サーバー用Rustワーカーは以前の試作で撤去済みで、Git履歴から参照できます。PC・Android本体のRust/QuickJSは維持します。未公開試作DBからの自動移行は追加せず、新しいDBパスを使います。

## 実装再開時点の検証（2026/10/22）

- TypeScript/React/サーバーの全113テストに合格。暗号化した実データの復号、誤った鍵の拒否も確認。
- Android ARM64デバッグAPKを生成。公開先未設定のため、ビルド検証用の`.invalid`ホストを指定。接続済みAPKとは区別。
- Androidの受信判定の単体テストに合格。停止、権限拒否、復号失敗、旧リビジョン・旧チャネル、期限、重複を確認。
- サーバーの実プロセス起動、二重起動拒否、強制終了と再起動・正常停止をローカルテストで確認。認証と配送のテストを実ntfyの成功とは扱わない。

`pnpm check`（113件＋Rust 26件、型・ビルド・テーマ・書式・差分チェック）に合格。Node.js 24でもサーバーの29テストに合格しました。APKは署名検証、アプリID・表示名、versionName 0.8.3 / versionCode 1、minSdk 24 / targetSdk 36、ARM64を確認。APKの16KB zip整列とRust/QuickJSを含む共有ライブラリーのLOAD整列（0x4000）も確認しました。16KB端末での起動確認は未実施です。

## 第4段階のVPS結合確認

2026/10/23にVPSの隔離ステージでNode.js 24.22.1・ntfy 2.32.0を使い、型チェック・実ntfyを含むサーバー67テスト・systemd定義検証に合格しました。利用者がバックアップ付き配備スクリプトをsudoで実行し、管理サービスと共有グループの配置成功を報告しました。API・管理サービス・ntfyの稼働をSSHで確認しました。公開の自動登録APIは認証なしGETへ401を返します。

公開HTTPSから一時的な2端末を発行し、API→Unixソケット管理プロセス→実ntfyを通して検証しました。本人の読み取り200、他端末の読み取り403、トピック横取り409、読み取り専用ユーザーの書き込み403を確認しました。通知先変更後は旧トピック403・新トピック200、購読停止API経由で`stopped`となった後はntfy認証401、再開後は同じ資格情報で200でした。両検証端末を削除し、ntfy資格情報とAPI Bearer認証の両方が401になることまで確認しました。既存端末の設定は変更していません。

ログイン情報のコピーに対応したAPKは`release/sureneco_v0.8.9_android_ntfy-login-copy_debug.apk`です。2026/10/23に利用者から、Android実機でログイン情報のコピー・ntfyへの貼り付け・「監視中」への移行・実際の通知受信まで成功した報告を受けました。これは利用者による実機確認で、こちらで直接操作・ログ観測した結果とは区別します。

別アプリ利用中の受信と体感約1分の遅延について利用者報告を受けています。以前は消灯中の未受信報告がありましたが、2026/10/24の追加テストでは11:56:45の募集が11:57台に通知され、到着時も画面が消えたままだったことを利用者が確認しました。この条件での消灯中受信は成功です。消灯継続時間と到着秒は未記録で、長時間消灯・Doze中の配送全体を確認したとは扱いません。以前の未受信原因は特定していません。

## 残っていること

1. **保留・ベータテストで確認**：長時間消灯後の通知受信。消灯中の受信成功例は確認済みですが、テスト実施が難しいため追加検証はベータテストへ持ち越します。端末・OS、消灯時間、電池制限、募集時刻・通知到着時刻、ntfy接続状態を記録します。完了扱いにはしません。
2. 管理サービス停止／復旧・VPS再起動をまたぐ、サーバー側の実環境確認を行う。
3. VPSのsystemd・TLS・バックアップ・削除・障害監視、同時接続・メモリ・転送量・通知遅延を実測する。登録人数の固定上限を設けない方針は無限の処理能力の保証ではない。
4. 公開用のアップロード鍵・接続先でAABを生成し、配布物への秘密情報混入、16KB端末、Play資料・申告を確認する。

OpenSpecの複合タスクは、実機確認済みの部分と消灯中・サーバー側復旧・配布などの残条件を区別して扱い、条件全体の確認前に完了とはしません。今回の実機確認完了を、配送運用・ストア提出・正式公開の完了とは扱いません。
