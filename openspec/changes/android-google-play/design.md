# Design

## Context

動機と合意範囲はproposal.mdを参照する。現行v0.8.3はdesktop featureが既定で、トレイ・OS操作・監視スレッドがsrc-tauri/src/desktop.rsにまとまっている。モバイルエントリーポイントとAndroid生成プロジェクトを追加し、ARM64デバッグAPKの生成は確認済み。募集判定はsrc/core、要求処理はsrc/backend/engine.ts、QuickJSホストはsrc-tauri/src/engine.rsに分離されている。

Androidの通知はサーバー監視＋Firebase Cloud Messaging（FCM）とする。VPS上の常駐Node.js版を試作したが、利用者の指示により実装を一旦中断した。契約済みエックスサーバーと1分程度の通知を前提に運用費を再検討する。以下はVPS案の設計記録であり、運用先の最終決定ではない。実装状況はdocs/server-progress.md、比較はdocs/operation-cost.mdを参照する。PHP版の検証をNode.js版の完了根拠には使わない。

## Goals / Non-Goals

**Goals:** VPS上の単一Node.jsサービスがAPIと監視・配送を担当し、既存TypeScriptコアとFirebase Admin SDKを利用して運用構成をまとめる。再起動後も取得基準と送信待ちを復元し、端末ごとの同期・停止・削除を保つ。

**Non-Goals:** PHPとの二重運用、自動データ移行、毎分cronへの依存、水平分散、端末内の24時間ポーリング、Foreground Service、Wake Lock、iOS、PC版の監視方式変更、サーバー契約・デプロイ・ストア公開。FCMの必達・即時配送も保証しない。

## Decisions

### 1. VPS上のNode.jsサービスにAPIとスケジューラーをまとめる

Node.js 24 LTSとTypeScriptでserver/を実装する。HTTP APIは127.0.0.1で待ち受け、Nginx等のHTTPSリバースプロキシから公開する。systemdの専用ユーザー・自動再起動で単一サービスを管理する。標準HTTP APIを使い、APIフレームワークは必須にしない。PHP-FPM・cron・運用サーバー上のRustコンパイルを要求しない。

SQLiteに端末の購読条件、設定リビジョン、取得基準、通知イベントとoutboxを保存する。Node.js組み込みのnode:sqliteを使い、初期構成は単一VPS・単一サービスとする。追加のネイティブDBモジュールとDB抽象化は入れない。Node.js 24でのAPIの成熟度に注意し、動作確認した24系のパッチ版を運用で固定する。書込みは短いトランザクションで確定し、ネットワーク取得や正規表現をトランザクション内で待たない。DBの所有権はOSが終了時に解放するロックで排他し、同じDBを使う二つ目のサービスは起動を拒否する。単にフラグファイルを作成する方式にはしない。

常駐スケジューラーは完了後に次の実行を予約し、前回が未完了の間は新しい監視回を重ねない。期限を迎えた購読を最長1秒の確認間隔で選び、同じ板・datの取得を監視回内で共有する。update_secとthread_update_secは60秒以上の整数、既定は60秒・300秒を維持する。70秒設定は約70秒後に処理対象となり、毎分cronの120秒回まで待たない。負荷・ネットワーク・FCMによる遅延はあり、即時通知を約束しない。PC版の20秒設定は変更しない。

1監視回の処理予算は50秒、監視に35秒まで、残りを配送に割り当てる。未処理の購読・送信待ちは次の監視回へ引き継ぐ。5chのHTTPS先制限、15秒・5MiB・リダイレクト拒否、文字コード変換を維持する。古い取得先・未処理の購読を優先し、一部の障害で全購読が止まらないようにする。

SIGTERMでは新規受付と次回予約を止め、実行中の仕事を上限付きで終了し、SQLiteを閉じる。強制終了時にも保存済み基準から再開する。systemdの停止猶予は処理予算より長くする。Node.jsの異常終了やVPS再起動はsystemdで復旧し、APIの生存と監視ループの完了時刻を別に確認する。

### 2. 認証と設定の同期

AndroidはFirebase Authenticationの匿名認証を使い、資格情報をネイティブ側で保持する。Node.js APIはFirebase Admin SDKでIDトークンの署名・発行者・対象プロジェクト・期限とApp Checkを検証し、App CheckのアプリIDも登録したAndroidアプリと照合する。UIDに紐づく自身の購読だけを操作させる。FCMトークンは配送先であり、APIの認証には使わない。公開前にApp CheckのPlay Integrity検証とUID・接続元単位のレート制限を有効にし、未検証アプリからの大量登録を防ぐ。

起動時に無条件登録せず、保存する情報を説明し、通知を許可した利用者がバックグラウンド通知を有効にしたときに登録する。同期対象は板URL、監視スレッド、更新周期、募集・締め・タイトル条件、NGと許可ワッチョイ、有効期間、FCMトークン。端末内の実行ファイルパスや設定フォルダーは送らない。

監視条件は共通の検証を通してから保存し、サーバーは単調増加するリビジョンを返す。Androidは変更要求中から旧リビジョンの通知を抑止し、受付結果と同期状態を表示する。通信失敗時に「同期済み」と表示しない。監視開始・条件変更・停止・削除は再送しても結果が増殖しない操作とする。

### 3. 判定と配信を永続化する

端末ごとに監視開始時の通知基準と処理済みレス番号を持ち、初回の過去募集を通知しない。Node.js側の募集判定は既存コアと同じNG、許可ワッチョイ、5桁ID、参照、締め、期限の振る舞いを満たす。既存のTypeScriptコアを再利用し、実行エンジンの差は共通の判定例で検証する。正規表現の互換性と隔離方式は実装前の検証対象とする。端末が非表示になっても取得基準は変えず、監視回ごとに新規募集を処理する。

判定はNode.jsの分離ワーカーで既存src/coreを呼び出す。固定のコードへJSON相当のデータを渡し、ユーザー入力をコードとして評価しない。親からの実時間1秒、入力16MiB・出力4MiB、ワーカーのJavaScriptヒープ32MiBを上限とし、超過時は強制終了して他の購読を継続する。ワーカーのヒープ制限はプロセス全体のメモリ上限ではないため、systemdでもサービス全体を制限する。APIでの正規表現の構文検証も同じ隔離経路を使う。PHP用のQuickJS実行ファイルはNode.js版では使わず、置換後に撤去する。PC・AndroidのQuickJSは維持する。

取得基準の更新とoutboxへの追加は同一トランザクションで確定する。取得・判定はDBの書き込みロック外で行い、保存時に購読の有効状態とリビジョンを再確認する。イベントIDは端末UID・板・スレッド・レス番号から一意にし、設定リビジョンは配送内容に付与するがイベントの重複キーには含めない。同じレスを設定変更や再起動で送り直さない。締めを確認した送信待ちは削除するが、イベントの重複防止情報は期限まで保持する。画面用200件の履歴上限によって古い送信待ちの締め判定を落とさない。

Firebase Admin SDKからFCMへdataメッセージを送信し、送信直前に購読状態、設定リビジョン、既知の締めと期限を再確認する。送信は少なくとも1回となり得るため、端末側もイベントIDを永続的に重複排除する。送信前に試行回数と次回時刻を確定し、送信後・成功記録前の停止でも同じイベントIDで再開する。送信は初回を含め5回までとし、60秒から指数的に待機時間を延ばし、最大15分と小さなジッター、FCMのRetry-Afterを考慮する。次の試行が期限以降になる場合は破棄し、イベントの重複防止記録は期限まで残す。送信失敗は期限内だけ上限付きバックオフで再試行時刻以降の監視回で再試行し、FCMのTTLも募集の残り有効期間以内にする。送信の一時エラー・認証エラーでは通知先を削除せず、FCMのUNREGISTERED応答だけで該当リビジョン・トークンの購読を削除する。送信中に更新された購読や他端末の情報には反映しない。監視に35秒まで、残り時間を配送へ割り当て、合計50秒を越えて次の仕事を始めない。サーバーが把握していない後続の締めを、送信済み通知へ即時反映することは保証しない。

### 4. FCMをAndroidネイティブで受信する

TauriのAndroidエントリーポイント、モバイル用Cargo構成、KotlinのFirebaseMessagingServiceを追加する。arboard・notify-rust・トレイ・single-instance・window-state・desktop updaterはAndroidへリンクしない。

FCMは利用者に表示する募集通知を目的とする高優先度dataメッセージを使用する。受信サービスがイベントID、購読リビジョン、期限、通知許可、ローカルの監視有効状態をネイティブの永続領域から確認し、追加のネットワーク取得なしに短時間で通知を表示する。自動表示されるnotificationペイロードに依存せず、旧設定や停止後のメッセージも端末側で落とせるようにする。FCMの上限内に収まるよう本文を切り詰める。

OS通知は表示中も非表示中もFCM受信に統一する。Reactの募集一覧は表示中に既存のローカル取得経路で更新できるが、その経路からOS通知は発行しない。画面復帰や設定再同期で通知基準を取り直したり、同じ募集を再通知したりしない。通知タップは検証済みのイベントからスレネコアラートの募集画面へ戻す。

FCMトークンの更新時は新しい配送先を登録して古い配送先を失効させる。無効トークンはサーバーから削除する。Android設定の強制停止・通知拒否・圏外・FCM側の遅延等では配送できないことがあるため、常時の即時配送を保証する表示はしない。

### 5. 停止・解除とデータの扱い

利用者が停止すると、端末側はまず監視有効フラグを落として以後の通知を抑止し、APIで購読停止と未送信outbox削除を行う。圏外でも端末の抑止は即時に行い、サーバー反映が未完了であることを表示して再接続時に再送する。

「サーバー登録を削除」は通知先・監視条件・その端末の配信履歴を削除する。通知権限が取り消された場合は表示時の再確認で同じ停止処理を行う。アンインストールはサーバーへ通知される保証がないため、FCMが無効と返した配送先を停止・削除する。トークンは更新時に同期し、操作がないという理由だけで有効な購読を停止しない。

履歴と送信待ちは有効期限後に掃除する。サーバーへ保存する対象・保存期間・解除方法を同意画面、プライバシーポリシー、Playの申告へ記載する。鍵・生トークン・NG全文を通常ログへ出さない。DBボリュームは暗号化された保管先とアクセス制限を使い、バックアップにも同じ削除方針を適用する。

### 6. 不正入力と運用障害への対処

HTTPS APIでは入力サイズ、監視対象数、登録頻度、処理待ち数を制限する。ユーザー定義のJavaScript正規表現は時間・メモリ上限のある分離ワーカーで実行し、上限超過時はその購読のエラーを表示して他の監視を止めない。任意URLの取得やユーザーからのFCM本文指定は受け付けない。

APIは購読ごとの最終取得成功時刻とエラーを返す。直近に確認できた情報であることを画面へ示し、オフライン時に正常稼働と断定しない。サーバーはバッチの最終開始・終了時刻、取得失敗、送信失敗、outbox滞留、DB容量を記録・監視する。監視ループが停止した状態をHTTP APIの応答成功だけで正常と扱わない。タイムアウト・強制終了・サービス再起動時の復旧をローカル結合テストと検証環境で確認する。

### 7. AABと公開の準備

Androidの生成プロジェクトと再現に必要な設定だけをGit管理し、SDKパス、鍵、ローカルビルド出力は除外する。API 24を初期minSdk、API 36以上をtarget/compile SDKとし、ARM64と16KBページサイズ対応を確認する。package:androidは署名付きAABを生成するだけで公開しない。

Androidの表示名は「スレネコアラート」、パッケージ名とKotlin namespaceは`sureneco.sakots`とする。TauriのAndroid専用設定でproductName/identifierを上書きし、Gradle・Activity・文字列リソースを一致させる。PC版の設定、Rust crate名、配布物の`sureneco`接頭辞は変更しない。旧Androidパッケージとは別アプリであり、互換用の旧Activity・識別子・データ移行処理は追加しない。FirebaseのAndroid登録も新しいパッケージ名を使う。

Firebaseの公開用接続設定、固定HTTPS APIの接続先、匿名認証とApp Checkの設定をAndroidのビルドへ与える。Admin SDKの資格情報やFCM送信用秘密鍵はサーバーだけに置き、AAB・ソース・ログへ含めない。versionNameはpackage.json、versionCodeは初回1から独立して管理し、アップロード鍵はデスクトップ更新鍵と分離する。

内部テストには実際のFirebaseと検証用サーバーが必要。Google Play向けの掲載文・プライバシーポリシー・データセーフティには、FCMと匿名端末認証、サーバーへ送る設定と保存期間を反映する。Androidアプリ更新はGoogle Play経由に限定する。

## Risks / Trade-offs

- サーバー運用費・停止時の通知欠落 → 契約・配備は利用者の確認後に行い、DB永続化、障害監視、期限内再試行と状態表示を用意する。無料運用を前提にしない。
- FCMの配送遅延・重複・端末の強制停止 → TTL、設定リビジョン、イベントID、端末での期限確認を使う。OS/通信制限下の必達を保証しない。
- 匿名認証APIの悪用と重い正規表現 → App Check、レート制限、入力上限、分離実行と期限超過テストで他の購読を保護する。
- Firebaseや5chの障害 → エラーと取得時刻を表示し、失敗時に古い募集を大量再送しない。認証失敗で公開APIへ迂回しない。
- QuickJS等のAndroidネイティブ依存 → クロスビルドと16KB端末の起動・判定確認を先に行う。PC版は回帰テストとクロスビルドで維持する。
- VPSの常駐サービス停止 → systemdの再起動、監視回の完了時刻とoutboxの監視、DBバックアップを用意する。更新周期の既定60秒を維持し、常駐化だけで即時配送を保証しない。
- V8とQuickJSの正規表現・メモリ制限の差 → 共通の判定例と分離ワーカーの強制終了を先に検証する。PHP版の成功をNode.js版の検証結果にしない。

## Migration Plan

Node.js版の回帰確認後、不要なPHP実装・専用テスト・Rustのサーバー用ワーカー・ビルド設定を撤去する。PHPのDBからの自動移行やPC版の設定変換は追加しない。Androidは専用領域で開始し、説明と同意、通知許可、サーバー登録が完了してからバックグラウンド通知を有効にする。検証環境で配信を確認した後にPlayの内部テストへ進む。障害時は新規登録・送信を停止し、端末の停止操作とデータ削除APIは維持する。

## Open Questions

契約先・ホスト名・FirebaseプロジェクトID・鍵の保管場所・Play Consoleの権限・掲載用連絡先は、配備作業で確定する。構成はVPS上の常駐Node.js＋SQLite＋Firebaseとし、公開前にVPSの費用、Node.jsとsystemd、HTTPS、バックアップと監視担当を確認する。未確定の情報を使って勝手に契約・配備・公開しない。
