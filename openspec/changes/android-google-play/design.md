# Design

## Context

動機と合意範囲はproposal.mdを参照する。現行v0.8.3はdesktop featureが既定で、トレイ・OS操作・監視スレッドがsrc-tauri/src/desktop.rsにまとまっている。モバイルエントリーポイントとAndroid生成プロジェクトを追加し、ARM64デバッグAPKの生成は確認済み。募集判定はsrc/core、要求処理はsrc/backend/engine.ts、QuickJSホストはsrc-tauri/src/engine.rsに分離されている。

Androidの通知はサーバー監視＋プッシュ通知とし、利用者が指定したサーバー構成はPHP＋cronである。毎分cronで各回1回処理して終了し、20秒間隔の短時間ループも使わないことで合意した。Node常駐サーバーを追加した実装は前提違いであり、PHPへの切り替え時に撤去する。Java 21、SDK/NDKとAndroid用Rustターゲットは準備済みだが、運用サーバー、Firebase、Play Consoleの接続と権限は未確認。

## Goals / Non-Goals

**Goals:** スマホの表示状態に依存しない監視をサーバーが担当し、既存の検出条件を使ってAndroidへ通知する。条件の同期、監視停止、重複・古い通知の抑止を端末とサーバーの両方で検証する。

**Non-Goals:** サーバーの常駐Node.js、cronバッチ内の待機・20秒間隔ループ、端末内の24時間ポーリング、Foreground Service、Wake Lock、iOS、PC版の監視方式変更、メール・パスワードによる利用者ログイン、サーバー契約・Firebase作成・デプロイ・ストア公開の自動実行。FCMによる必達・即時配送も保証しない。

## Decisions

### 1. PHPのHTTPS APIと毎分cronの単発バッチを追加する

server/にPHPのHTTPS APIとCLIバッチを実装する。APIはPHPのWeb実行環境で要求ごとに処理し、バッチはcronの`* * * * *`で毎分起動して、その時点で期限を迎えた取得・判定・配信を1回処理して終了する。WebViewのタイマー、常駐プロセス、sleepでの次回待ちには依存させない。必要なのはPHPのWeb・CLI実行環境、SQLite、HTTPS通信と毎分cronであり、運用先にNode.jsは要求しない。Node.js・pnpmはAndroidの開発・ビルド用にのみ使う。

永続DBはSQLiteを初期構成とし、端末、購読条件と設定リビジョン、取得済みレス番号、配信済みイベント、送信待ちのoutboxを保存する。APIとバッチは別プロセスから同じDBを使い、必要な更新をトランザクションで確定する。同一DBのバッチは固定ロックファイルの`flock(LOCK_EX | LOCK_NB)`で単一所有にし、重複実行は処理せず終了する。ファイルは削除せず、通常終了・異常終了ともOSのロック解放により次回起動できる。水平分散とDB製品の抽象化は入れない。

5chの取得先制限・15秒・5MiB・リダイレクト拒否を維持する。同じ板・スレッドの取得は1回のバッチ内で共有し、端末ごとのupdate_secとthread_update_secに従って判定する。Androidのサーバー設定はどちらも60秒以上の整数とし、既定値はupdate_secが60秒、thread_update_secが300秒。設定間隔を経過した後の最初のcron実行で処理するため、例えば70秒設定は通常約120秒間隔となり、負荷・cronの遅延・障害でさらに遅れる場合がある。PC版の既定20秒・下限20秒は変更しない。

各バッチには1分未満の実行予算を設け、未処理分と送信待ちはDBへ保持して次回へ引き継ぐ。バックオフ待ちをプロセス内でsleepせず、保存した再試行時刻と有効期限を次回cronで確認する。毎回の起動で通知基準を作り直さず、前回の永続状態から再開する。

### 2. 認証と設定の同期

AndroidはFirebase Authenticationの匿名認証を使い、資格情報をネイティブ側で保持する。PHP APIはFirebaseのIDトークンの署名・発行者・対象プロジェクト・期限を検証し、UIDに紐づく自身の購読だけを操作させる。FCMトークンは配送先であり、APIの認証には使わない。公開前にApp CheckのPlay Integrity検証とUID・接続元単位のレート制限を有効にし、未検証アプリからの大量登録を防ぐ。

起動時に無条件登録せず、保存する情報を説明し、通知を許可した利用者がバックグラウンド通知を有効にしたときに登録する。同期対象は板URL、監視スレッド、更新周期、募集・締め・タイトル条件、NGと許可ワッチョイ、有効期間、FCMトークン。端末内の実行ファイルパスや設定フォルダーは送らない。

監視条件は共通の検証を通してから保存し、サーバーは単調増加するリビジョンを返す。Androidは変更要求中から旧リビジョンの通知を抑止し、受付結果と同期状態を表示する。通信失敗時に「同期済み」と表示しない。監視開始・条件変更・停止・削除は再送しても結果が増殖しない操作とする。

### 3. 判定と配信を永続化する

端末ごとに監視開始時の通知基準と処理済みレス番号を持ち、初回の過去募集を通知しない。PHP側の募集判定は既存コアと同じNG、許可ワッチョイ、5桁ID、参照、締め、期限の振る舞いを満たす。既存の判定例を共通の入出力として検証し、JavaScript正規表現をPCREへ単純置換して同等とみなさない。正規表現の互換性と隔離方式は実装前の検証対象とする。端末が非表示になっても取得基準は変えず、cronごとに新規募集を処理する。

取得基準の更新とoutboxへの追加は同一トランザクションで確定する。イベントIDは端末UID・板・スレッド・レス番号から一意にし、設定リビジョンは配送内容に付与するがイベントの重複キーには含めない。同じレスを設定変更や再起動で送り直さない。

PHPからFCM HTTP v1 APIへ送信し、送信直前に購読状態、設定リビジョン、既知の締めと期限を再確認する。送信は少なくとも1回となり得るため、端末側もイベントIDを永続的に重複排除する。送信失敗は期限内だけ上限付きバックオフで次回以降のcronから再試行し、FCMのTTLも募集の残り有効期間以内にする。サーバーが把握していない後続の締めを、送信済み通知へ即時反映することは保証しない。

### 4. FCMをAndroidネイティブで受信する

TauriのAndroidエントリーポイント、モバイル用Cargo構成、KotlinのFirebaseMessagingServiceを追加する。arboard・notify-rust・トレイ・single-instance・window-state・desktop updaterはAndroidへリンクしない。

FCMは利用者に表示する募集通知を目的とする高優先度dataメッセージを使用する。受信サービスがイベントID、購読リビジョン、期限、通知許可、ローカルの監視有効状態をネイティブの永続領域から確認し、追加のネットワーク取得なしに短時間で通知を表示する。自動表示されるnotificationペイロードに依存せず、旧設定や停止後のメッセージも端末側で落とせるようにする。FCMの上限内に収まるよう本文を切り詰める。

OS通知は表示中も非表示中もFCM受信に統一する。Reactの募集一覧は表示中に既存のローカル取得経路で更新できるが、その経路からOS通知は発行しない。画面復帰や設定再同期で通知基準を取り直したり、同じ募集を再通知したりしない。通知タップは検証済みのイベントからsurenecoの募集画面へ戻す。

FCMトークンの更新時は新しい配送先を登録して古い配送先を失効させる。無効トークンはサーバーから削除する。Android設定の強制停止・通知拒否・圏外・FCM側の遅延等では配送できないことがあるため、常時の即時配送を保証する表示はしない。

### 5. 停止・解除とデータの扱い

利用者が停止すると、端末側はまず監視有効フラグを落として以後の通知を抑止し、APIで購読停止と未送信outbox削除を行う。圏外でも端末の抑止は即時に行い、サーバー反映が未完了であることを表示して再接続時に再送する。

「サーバー登録を削除」は通知先・監視条件・その端末の配信履歴を削除する。通知権限が取り消された場合は表示時の再確認で同じ停止処理を行う。アンインストールはサーバーへ通知される保証がないため、FCMが無効と返した配送先を停止・削除する。トークンは更新時に同期し、操作がないという理由だけで有効な購読を停止しない。

履歴と送信待ちは有効期限後に掃除する。サーバーへ保存する対象・保存期間・解除方法を同意画面、プライバシーポリシー、Playの申告へ記載する。鍵・生トークン・NG全文を通常ログへ出さない。DBボリュームは暗号化された保管先とアクセス制限を使い、バックアップにも同じ削除方針を適用する。

### 6. 不正入力と運用障害への対処

HTTPS APIでは入力サイズ、監視対象数、登録頻度、処理待ち数を制限する。ユーザー定義のJavaScript正規表現は時間・メモリ上限のある分離ワーカーで実行し、上限超過時はその購読のエラーを表示して他の監視を止めない。任意URLの取得やユーザーからのFCM本文指定は受け付けない。

APIは購読ごとの最終取得成功時刻とエラーを返す。直近に確認できた情報であることを画面へ示し、オフライン時に正常稼働と断定しない。サーバーはバッチの最終開始・終了時刻、取得失敗、送信失敗、outbox滞留、DB容量を記録・監視する。cronが起動しない状態をPHP APIの応答成功だけで正常と扱わない。タイムアウト・強制終了・次回cron起動時の復旧をローカル結合テストと検証環境で確認する。

### 7. AABと公開の準備

Androidの生成プロジェクトと再現に必要な設定だけをGit管理し、SDKパス、鍵、ローカルビルド出力は除外する。API 24を初期minSdk、API 36以上をtarget/compile SDKとし、ARM64と16KBページサイズ対応を確認する。package:androidは署名付きAABを生成するだけで公開しない。

Firebaseの公開用接続設定、固定HTTPS APIの接続先、匿名認証とApp Checkの設定をAndroidのビルドへ与える。Admin SDKの資格情報やFCM送信用秘密鍵はサーバーだけに置き、AAB・ソース・ログへ含めない。versionNameはpackage.json、versionCodeは初回1から独立して管理し、アップロード鍵はデスクトップ更新鍵と分離する。

内部テストには実際のFirebaseと検証用サーバーが必要。Google Play向けの掲載文・プライバシーポリシー・データセーフティには、FCMと匿名端末認証、サーバーへ送る設定と保存期間を反映する。Androidアプリ更新はGoogle Play経由に限定する。

## Risks / Trade-offs

- サーバー運用費・停止時の通知欠落 → 契約・配備は利用者の確認後に行い、DB永続化、障害監視、期限内再試行と状態表示を用意する。無料運用を前提にしない。
- FCMの配送遅延・重複・端末の強制停止 → TTL、設定リビジョン、イベントID、端末での期限確認を使う。OS/通信制限下の必達を保証しない。
- 匿名認証APIの悪用と重い正規表現 → App Check、レート制限、入力上限、分離実行と期限超過テストで他の購読を保護する。
- Firebaseや5chの障害 → エラーと取得時刻を表示し、失敗時に古い募集を大量再送しない。認証失敗で公開APIへ迂回しない。
- QuickJS等のAndroidネイティブ依存 → クロスビルドと16KB端末の起動・判定確認を先に行う。PC版は回帰テストとクロスビルドで維持する。
- 毎分cronの粒度と実行予算 → Androidのサーバー監視は最短約1分と説明し、20秒更新や即時配送を案内しない。実行予算で未処理になった仕事は次回へ引き継ぎ、期限切れ通知は送らない。
- PHPと既存JavaScriptコアの判定差 → 共通の判定例と正規表現の互換性・実行上限を先に検証する。未確認の移植を動作同等と扱わない。

## Migration Plan

PC版の設定変換や自動移行は追加しない。Androidは専用領域で開始し、説明と同意、通知許可、サーバー登録が完了してからバックグラウンド通知を有効にする。検証環境で配信を確認した後にPlayの内部テストへ進む。障害時は新規登録・送信を停止し、端末の停止操作とデータ削除APIは維持する。

## Open Questions

契約先・ホスト名・FirebaseプロジェクトID・鍵の保管場所・Play Consoleの権限・掲載用連絡先は、ローカル実装後の配備作業で確定できる。アーキテクチャはPHPのHTTPS API＋毎分cronの単発バッチ＋永続DB＋Firebaseに固定し、公開前にはPHPの必要拡張、毎分cronと実行制限、これらの実値と費用負担、監視担当を確認する。未確定の運用情報を使って勝手に契約・配備・公開しない。
