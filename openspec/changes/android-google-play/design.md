# Design

## Context

動機と合意範囲はproposal.mdを参照する。現行v0.8.3はdesktop featureが既定で、トレイ・OS操作・監視スレッドがsrc-tauri/src/desktop.rsにまとまっている。モバイルエントリーポイントとAndroid生成プロジェクトを追加し、ARM64デバッグAPKの生成は確認済み。募集判定はsrc/core、要求処理はsrc/backend/engine.ts、QuickJSホストはsrc-tauri/src/engine.rsに分離されている。

Androidの通知はUnifiedPush＋自前ntfyとする。Node.js＋VPSの監視とSQLiteは維持し、Firebase認証・App Check・FCMを置き換える。実装を再開しており、現行ソースは端末認証とWeb Pushへ置き換えた。採用構成はdocs/unifiedpush-ntfy.md、確認済み範囲はdocs/server-progress.mdを参照する。旧試作のテストを新方式の実配送成功の根拠にはしない。

## Goals / Non-Goals

**Goals:** VPS上の単一Node.jsサービスがAPIと監視・配送を担当し、既存TypeScriptコアと自前ntfy・Web Pushを利用して運用構成をまとめる。再起動後も取得基準と送信待ちを復元し、端末ごとの同期・停止・削除を保つ。

**Non-Goals:** PHPとの二重運用、自動データ移行、毎分cronへの依存、水平分散、端末内の24時間ポーリング、スレネコアラート自身のForeground Service・Wake Lock、iOS、PC版の監視方式変更、サーバー契約・デプロイ・ストア公開。プッシュの必達・即時配送も保証しない。

## Decisions

### 1. VPS上のNode.jsサービスにAPIとスケジューラーをまとめる

Node.js 24 LTSとTypeScriptでserver/を実装する。HTTP APIは127.0.0.1で待ち受け、Nginx等のHTTPSリバースプロキシから公開する。systemdの専用ユーザー・自動再起動で単一サービスを管理する。標準HTTP APIを使い、APIフレームワークは必須にしない。PHP-FPM・cron・運用サーバー上のRustコンパイルを要求しない。

SQLiteに端末の購読条件、設定リビジョン、取得基準、通知イベントとoutboxを保存する。Node.js組み込みのnode:sqliteを使い、初期構成は単一VPS・単一サービスとする。追加のネイティブDBモジュールとDB抽象化は入れない。Node.js 24でのAPIの成熟度に注意し、動作確認した24系のパッチ版を運用で固定する。書込みは短いトランザクションで確定し、ネットワーク取得や正規表現をトランザクション内で待たない。DBの所有権はOSが終了時に解放するロックで排他し、同じDBを使う二つ目のサービスは起動を拒否する。単にフラグファイルを作成する方式にはしない。

常駐スケジューラーは完了後に次の実行を予約し、前回が未完了の間は新しい監視回を重ねない。期限を迎えた購読を最長1秒の確認間隔で選び、同じ板・datの取得を監視回内で共有する。update_secとthread_update_secは60秒以上の整数、既定は60秒・300秒を維持する。70秒設定は約70秒後に処理対象となり、毎分cronの120秒回まで待たない。負荷・ネットワーク・ntfy・端末による遅延はあり、即時通知を約束しない。PC版の20秒設定は変更しない。

1監視回の処理予算は50秒、監視に35秒まで、残りを配送に割り当てる。未処理の購読・送信待ちは次の監視回へ引き継ぐ。5chのHTTPS先制限、15秒・5MiB・リダイレクト拒否、文字コード変換を維持する。古い取得先・未処理の購読を優先し、一部の障害で全購読が止まらないようにする。

SIGTERMでは新規受付と次回予約を止め、実行中の仕事を上限付きで終了し、SQLiteを閉じる。強制終了時にも保存済み基準から再開する。systemdの停止猶予は処理予算より長くする。Node.jsの異常終了やVPS再起動はsystemdで復旧し、APIの生存と監視ループの完了時刻を別に確認する。

### 2. 認証と設定の同期

端末認証は自前APIで行う。同意後のPOST /v1/deviceで端末IDと256bitのランダム認証トークンを発行し、サーバーはハッシュだけを保存する。Androidはネイティブ専用領域で保護し、バックアップ・ログへ含めない。所有者本人の購読だけをBearer認証で操作させ、POST /v1/device/rotateで旧トークンを失効、DELETE /v1/deviceで端末資格情報と購読を削除する。配送先URLはAPI認証に使わず、APKへ全端末共通の秘密を埋め込まない。端末・接続元単位の発行頻度・操作回数・入力上限を設ける。この認証はAPKの真正性を証明せず、App Checkと同等の保証はしない。

起動時に無条件登録せず、保存する情報を説明し、通知を許可した利用者がバックグラウンド通知を有効にしたときに登録する。同期対象は板URL、監視スレッド、更新周期、募集・締め・タイトル条件、NGと許可ワッチョイ、有効期間、UnifiedPush通知先と暗号化鍵。端末内の実行ファイルパスや設定フォルダーは送らない。

監視条件は共通の検証を通してから保存し、サーバーは単調増加するリビジョンを返す。Androidは変更要求中から旧リビジョンの通知を抑止し、受付結果と同期状態を表示する。通信失敗時に「同期済み」と表示しない。監視開始・条件変更・停止・削除は再送しても結果が増殖しない操作とする。

端末認証の更新ではAndroidが新しい256bitトークンを生成して専用領域へ更新候補として保存し、`POST /v1/device/rotate`へ`{newToken}`を送ります。応答が切れた場合は新トークンで本人の購読を照会して更新を確認できるまで旧・新の候補を保持します。起動時に30日を経過していれば更新し、途中の更新は同期前に再試行します。

### 3. 判定と配信を永続化する

端末ごとに監視開始時の通知基準と処理済みレス番号を持ち、初回の過去募集を通知しない。Node.js側の募集判定は既存コアと同じNG、許可ワッチョイ、5桁ID、参照、締め、期限の振る舞いを満たす。既存のTypeScriptコアを再利用し、実行エンジンの差は共通の判定例で検証する。正規表現の互換性と隔離方式は実装前の検証対象とする。端末が非表示になっても取得基準は変えず、監視回ごとに新規募集を処理する。

判定はNode.jsの分離ワーカーで既存src/coreを呼び出す。固定のコードへJSON相当のデータを渡し、ユーザー入力をコードとして評価しない。親からの実時間1秒、入力16MiB・出力4MiB、ワーカーのJavaScriptヒープ32MiBを上限とし、超過時は強制終了して他の購読を継続する。ワーカーのヒープ制限はプロセス全体のメモリ上限ではないため、systemdでもサービス全体を制限する。APIでの正規表現の構文検証も同じ隔離経路を使う。PHP用のQuickJS実行ファイルはNode.js版では使わず、置換後に撤去する。PC・AndroidのQuickJSは維持する。

取得基準の更新とoutboxへの追加は同一トランザクションで確定する。取得・判定はDBの書き込みロック外で行い、保存時に購読の有効状態とリビジョンを再確認する。イベントIDは端末UID・板・スレッド・レス番号から一意にし、設定リビジョンは配送内容に付与するがイベントの重複キーには含めない。同じレスを設定変更や再起動で送り直さない。締めを確認した送信待ちは削除するが、イベントの重複防止情報は期限まで保持する。画面用200件の履歴上限によって古い送信待ちの締め判定を落とさない。

Node.jsから自前ntfyへRFC8291（aes128gcm）対応のWeb Pushライブラリーで暗号化して送信する。VAPID秘密鍵はサーバーにだけ置く。配送内容にはイベントID・設定リビジョン・通知先世代・期限を持たせ、送信直前に有効状態・既知の締め・期限を再確認する。outboxと試行回数・次回時刻を送信前に保存し、成功記録前の停止では同じイベントIDで再開する。初回込み最大5回、60秒から最大15分の指数バックオフとジッター、Retry-Afterを考慮し、有効期限以降の再試行は破棄する。Web Push TTLは募集の残り有効時間以内とする。一時障害・認証失敗で購読を削除せず、無効通知先の応答は採用ntfyで検証する。FCMのUNREGISTEREDに相当する挙動があるとは仮定しない。送信中に更新された通知先や別端末へ失敗結果を反映しない。合計50秒の処理予算を維持し、ntfyの受付成功と端末表示成功は区別する。把握前の後続の締めを送信済み通知へ即時反映する保証はしない。

### 4. UnifiedPushをAndroidネイティブで受信する

AndroidのKotlin層にUnifiedPush connectorを組み込む。初期対応の中継アプリは自前ntfyへ接続するntfyとし、Firebaseを含まない案内にはF-Droid版を使う。未導入・選択・登録中・失敗・通知先変更・登録解除を画面へ反映する。スレネコアラートに監視用のForeground Serviceは追加せず、接続維持は中継アプリが担当する。arboard・notify-rust・トレイ・single-instance・window-state・desktop updaterはAndroidへリンクしない。

connectorから通知先URL・p256dh公開鍵・auth secretを取得し、認証済みAPIへ同期する。設定済みの自前ntfyのHTTPS origin・通知先パスだけを許可する。リダイレクトと内部IPへの送信を拒否し、毎回DNS解決先を検査する。新規・更新チャネルには短時間有効・一回限りのチャレンジを暗号化配送し、端末からの認証済み応答で所有を確認してから監視を有効にする。別端末と競合する通知先は拒否する。

復号したデータをネイティブ受信処理で検証し、WebViewが未起動でもイベントID・リビジョン・通知先世代・期限・権限・ローカル停止状態を専用領域から確認してOS通知を表示する。本文はWeb Pushの上限内へ切り詰め、未検証データを直接表示しない。表示中のローカル一覧更新からOS通知は出さず、通知タップで募集画面へ戻す。

ntfyの認証・トピックACLは端末ごとに分離する。全端末へ同じ読み取り権限を配らず、UnifiedPush用の書き込み権限と本人の購読権限を分ける。資格情報の払い出しとconnectorの通知先登録・削除を一連の結合テストで確認する。通常のntfyトピック通知を端末側で重ねて表示しない。

### 5. 停止・解除とデータの扱い

利用者が停止すると、端末側はまず監視有効フラグを落として以後の通知を抑止し、APIで購読停止と未送信outbox削除を行う。圏外でも端末の抑止は即時に行い、サーバー反映が未完了であることを表示して再接続時に再送する。

「サーバー登録を削除」は通知先・監視条件・取得基準・配信履歴を削除する。端末認証を消す操作はDELETE /v1/deviceに分ける。権限取り消しやconnectorの登録解除では端末で即座に抑止し、サーバーへ停止を再送する。アンインストールの即時検知は保証できない。チャネル失効を確認できれば配送を止めるが、ntfyで確認できない残存登録を即時削除済みとは扱わない。アプリを表示しないという理由だけで有効な購読を止めない。

履歴と送信待ちは有効期限後に掃除する。サーバーへ保存する対象・保存期間・解除方法を同意画面、プライバシーポリシー、Playの申告へ記載する。鍵・生トークン・NG全文を通常ログへ出さない。DBボリュームは暗号化された保管先とアクセス制限を使い、バックアップにも同じ削除方針を適用する。

### 6. 不正入力と運用障害への対処

HTTPS APIでは入力サイズ、監視対象数、登録頻度、処理待ち数を制限する。ユーザー定義のJavaScript正規表現は時間・メモリ上限のある分離ワーカーで実行し、上限超過時はその購読のエラーを表示して他の監視を止めない。任意URLの取得やユーザーからの通知本文指定は受け付けない。

APIは購読ごとの最終取得成功時刻とエラーを返す。直近に確認できた情報であることを画面へ示し、オフライン時に正常稼働と断定しない。サーバーはバッチの最終開始・終了時刻、取得失敗、送信失敗、outbox滞留、DB容量を記録・監視する。監視ループが停止した状態をHTTP APIの応答成功だけで正常と扱わない。タイムアウト・強制終了・サービス再起動時の復旧をローカル結合テストと検証環境で確認する。

### 7. AABと公開の準備

Androidの生成プロジェクトと再現に必要な設定だけをGit管理し、SDKパス、鍵、ローカルビルド出力は除外する。API 24を初期minSdk、API 36以上をtarget/compile SDKとし、ARM64と16KBページサイズ対応を確認する。package:androidは署名付きAABを生成するだけで公開しない。

Androidの表示名は「スレネコアラート」、パッケージ名とKotlin namespaceは`sureneco.sakots`とする。TauriのAndroid専用設定でproductName/identifierを上書きし、Gradle・Activity・文字列リソースを一致させる。PC版の設定、Rust crate名、配布物の`sureneco`接頭辞は変更しない。旧Androidパッケージとは別アプリであり、互換用の旧Activity・識別子・データ移行処理は追加しない。

固定HTTPS APIと自前ntfyのoriginをAndroidの公開用ビルド設定へ与える。Firebase公開識別子・SDKは撤去し、ntfy管理資格情報やVAPID秘密鍵・Android署名鍵をAABへ含めない。versionNameはpackage.json、versionCodeは初回1から独立管理し、アップロード鍵はPC版更新鍵と分離する。

内部テストには実際の自前ntfyと検証用VPS・Androidが必要。掲載文・プライバシーポリシー・データセーフティには中継アプリの導入、端末別認証、送信する設定・通知先・暗号化鍵、保存期間・削除方法を反映する。Android更新はGoogle Play経由とする。

## Risks / Trade-offs

- サーバー運用費・停止時の通知欠落 → 契約・配備は利用者の確認後に行い、DB永続化、障害監視、期限内再試行と状態表示を用意する。無料運用を前提にしない。
- ntfyの配送遅延・重複・中継アプリの停止・端末の強制停止 → TTL、設定リビジョン、イベントID、端末での期限確認を使う。OS/通信制限下の必達を保証しない。
- 端末登録APIの悪用と重い正規表現 → 端末別認証、レート制限、入力上限、分離実行と期限超過テストで他の購読を保護する。
- ntfyや5chの障害 → エラーと取得時刻を表示し、失敗時に古い募集を大量再送しない。認証失敗で公開APIへ迂回しない。
- QuickJS等のAndroidネイティブ依存 → クロスビルドと16KB端末の起動・判定確認を先に行う。PC版は回帰テストとクロスビルドで維持する。
- VPSの常駐サービス停止 → systemdの再起動、監視回の完了時刻とoutboxの監視、DBバックアップを用意する。更新周期の既定60秒を維持し、常駐化だけで即時配送を保証しない。
- V8とQuickJSの正規表現・メモリ制限の差 → 共通の判定例と分離ワーカーの強制終了を先に検証する。PHP版の成功をNode.js版の検証結果にしない。
- 中継アプリの追加と常時接続 → 導入・電池設定・未登録の案内と消灯中の実機検証を行う。Node.jsに加えてntfyのメモリ・接続数・転送量・ファイル記述子を測る。

## Migration Plan

Firebase試作の認証・配送・設定・依存・テストを端末認証とUnifiedPushへ置き換えた。旧DBの自動移行やFCMフォールバックは追加しない。既存の共有取得・判定・outboxを回帰確認し、実際の自前ntfyと端末で停止・削除・復旧を検証してからPlay内部テストへ進む。障害時は新規登録・送信を止め、既存端末の停止・削除は維持する。

## Open Questions

VPS契約先・APIとntfyのホスト名・鍵保管先・Play Consoleの権限・掲載連絡先は配備時に確定する。採用構成はNode.js＋SQLite＋自前ntfy。費用・バックアップ・監視担当の確認前に契約・配備・公開しない。
